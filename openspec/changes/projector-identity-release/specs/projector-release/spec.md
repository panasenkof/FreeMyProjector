## ADDED Requirements

### Requirement: Отдельная идентичность Android-приложения
Приложение SHALL иметь package ID `com.panasenkof.freemyprojector`, метку `FreeMyProjector`, версионирование и корректные имена экспортируемых/внутренних Android компонентов.

#### Scenario: Создан unsigned APK в обычном CI
- **WHEN** Android build выполняется на PR
- **THEN** `aapt2 dump badging` показывает новый package ID, minSdk 28 и targetSdk 33, а Java Activity/Service/Receiver в манифесте указывают на реально существующие классы
#### Scenario: Компоненты собственного HOME
- **WHEN** приложение формирует имена компонентов HOME, Settings, Screensaver или RemoteKeyService
- **THEN** package prefix равен `com.panasenkof.freemyprojector`, а component class совпадает с полным именем класса в manifest; фактическое переключение HOME в рамках P-03 не производится

### Requirement: Fail-closed подпись APK
Скрипт сборки SHALL допускать приватное подписание только при явных параметрах keystore, alias и паролей, не создавать ключ с предсказуемым паролем и не выдавать unsigned APK за подписанный.

#### Scenario: Сборка без ключа
- **WHEN** запускается локальная сборка без signing credentials
- **THEN** она завершается сообщением о необходимости signing credentials, не создаёт подписанный APK и не генерирует keystore
#### Scenario: Проверочная сборка CI
- **WHEN** указан `FMP_BUILD_UNSIGNED=1`
- **THEN** выполняется компиляция и полученный APK остаётся неподписанным
#### Scenario: Приватная подпись
- **WHEN** валидные signing credentials явно переданы при локальной или release-сборке
- **THEN** подпись проходит `apksigner verify`, итоговый APK сохраняется в `FreeMyProjector.apk`

### Requirement: Изолированная публикация установки
Workflow SHALL подписывать и публиковать APK исключительно при ручном запуске из `main` с настроенными секретами; ordinary PR CI SHALL иметь только read-доступ и не получать секреты.

#### Scenario: Нет секретов подписи
- **WHEN** пользователь запускает релиз без всех требуемых GitHub Secrets
- **THEN** запуск завершается с понятной ошибкой до публикации, не создаёт release/tag и не сохраняет приватный ключ
#### Scenario: Первый подписанный выпуск
- **WHEN** секреты настроены, пользователь вручную запускает release-workflow с `main` и версия не опубликована ранее
- **THEN** workflow проверяет подпись, метаданные и SHA256, а затем создаёт prerelease с подписанным APK
#### Scenario: Повторное использование версии
- **WHEN** тег версии уже существует
- **THEN** workflow останавливается, не перезаписывая активный APK и не подменяя сертификат

### Requirement: Предсказуемые обновления и защита секрета
Документация SHALL объяснять необходимость стабильного сертификата и возрастающего `versionCode`, резервного хранения ключа и отсутствия секретов в репозитории/логах.

#### Scenario: Подготовка следующего релиза
- **WHEN** номер версии меняется
- **THEN** `versionCode` увеличивается по сравнению с предыдущим выпуском, подпись сохраняет исходный сертификат, а пользователь понимает как проверить сертификат и архивировать ключ офлайн

### Requirement: Безопасность устройства
P-03 SHALL не устанавливать приложения автоматически, не подключаться по ADB и не менять настройки HOME/системных пакетов.

#### Scenario: Любой запуск P-03 CI
- **WHEN** запускается сборка или релиз
- **THEN** не выполняются `adb install`, `set-home-activity`, `pm disable-user` или команды изменения конфигурации проектора
