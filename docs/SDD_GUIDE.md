# Spec-Driven Development в FreeMyProjector

**Коротко:** SDD — сначала описываем результат и способ его проверки, затем строим архитектуру, задачи и код. Для этого используем [OpenSpec](https://github.com/Fission-AI/OpenSpec) и обычные Markdown-файлы в GitHub. Владельцу не требуется знать технические термины или устанавливать CLI, чтобы принимать решения.

## Что создаётся и зачем

| Артефакт | На человеческом языке | Кто готовит | Кто проверяет |
|---|---|---|---|
| `PLAN.md` | Очередь работ, приоритеты, что нужно проверить | ИИ + владелец | Владелец проекта |
| `proposal.md` | Зачем изменение, границы, чего не делаем | ИИ | Владелец утверждает цель |
| `specs/<capability>/spec.md` | **Что должно получиться** и как это проверить | ИИ | Владелец утверждает поведение |
| `design.md` | **Как реализовать:** модули, данные, риски, откат | ИИ | ИИ; спорные решения — владельцу |
| `tasks.md` | Порядок шагов, тесты и чек-листы | ИИ | ИИ; приёмочные проверки — владелец |
| `openspec/specs/<capability>/spec.md` | Что фактически подтверждено и поддерживается | ИИ после проверки | Владелец подтверждает реальные тесты |

**Первое правило:** `openspec/changes` хранит предлагаемые, ещё не обязательно реализованные требования; `openspec/specs` — подтверждённое действующее поведение. Не копировать «будущее» в действующее до завершения проверки.

## Как будем работать

1. Ты пишешь: «Хочу, чтобы после нажатия HOME открывался FreeMyProjector, а оригинальный экран можно было легко вернуть».
2. Я изучаю исходники, ограничение Xiaomi/Android и составляю proposal, проверяемые требования, design, tasks. Сразу перечисляю сомнения и рискованные действия.
3. Ты просматриваешь короткое описание и отвечаешь «согласен» либо уточняешь поведение. Не требуется читать все технические детали.
4. После утверждения я делаю отдельный PR с реализацией и проверками. Если появляется новый риск — обновляю спецификацию **до** опасного действия.
5. Автотесты и тесты на GitHub Actions могут подтвердить сборку, но не работоспособность на твоём проекторе. Я выдаю короткий ручной чек-лист.
6. Только после твоего результата «проверено» закрываем этап в `PLAN.md`, синхронизируем актуальную spec и архивируем change.

Схема: **идея → предложение → требования → архитектура → задачи → PR → автотесты → ручная проверка → подтверждение → архив**.

## Как выглядит проверяемое требование

Пример (не утверждение о том, что это уже работает):

```md
### Requirement: Запуск приложения с пульта
Приложение SHALL принимать команды стандартного пульта Android TV.

#### Scenario: Кнопка назад
- **WHEN** пользователь нажимает BACK на главном экране
- **THEN** приложение сохраняет управляемость и не показывает чёрный экран
```

Плохое требование: «Сделать хороший быстрый интерфейс». Хорошее: «На конкретной прошивке кнопки LEFT/RIGHT/OK/BACK срабатывают корректно в 20 последовательных действиях; лаги и сбои зафиксированы в протоколе теста». Численные бюджеты FPS/памяти устанавливаем по замерам, а не выдумываем заранее.

## Чем пользоваться прямо сейчас

**Ничего дополнительно устанавливать не обязательно:** ChatGPT уже работает с GitHub через подключённую интеграцию; документы и PR можно готовить здесь. OpenSpec сейчас заводим как **совместимую структуру Markdown**; наличие файлов не означает, что CLI установлен и протестирован.

Если позже понадобится запускать OpenSpec локально на компьютере:

```sh
# Требуется Node.js версии, совместимой с текущим релизом OpenSpec (на октябрь 2026 — 20.19.0+).
npm install -g @fission-ai/openspec@latest
# Запускать в клоне FreeMyProjector:
openspec init
# Выбрать используемый AI-инструмент и проверить созданные файлы в git diff.
```

Команда `openspec init` может создавать инструкции для конкретных AI-инструментов. **Не запускать её поверх существующих файлов без просмотра diff**. Будущую интеграцию в Cursor/Claude Code/Codex настраиваем по выбору реального инструмента; необязательно делать это сейчас.

Официальный рабочий цикл OpenSpec: `/opsx:explore` (необязательно) → `/opsx:propose` → `/opsx:apply` → `/opsx:sync` → `/opsx:archive`. Команды в чате появляются только в поддерживаемом IDE/агенте после инициализации. В этом чате достаточно обычной фразы «сделай спецификацию для P-02».

Периодически можно запускать локально `openspec validate <change-name>`, если установлена подходящая версия CLI. Не считать локальную проверку пройденной, пока она не выполнена.

## Где и когда нужны дополнительные инструменты

| Инструмент | Сейчас | Для чего |
|---|---|---|
| **GitHub** (подключён) | Да | Код, PR, история решений, ревью и GitHub Actions |
| **OpenSpec CLI** | Необязательно | Генерировать и проверять спецификации, команды в IDE |
| **Android SDK + JDK 17+ + ADB** | Позже на этапе сборки и диагностики | Создание APK и чтение параметров устройства |
| **GitHub Actions** | Добавить в P-02 | Автосборка, тесты и сохранение APK |
| **Cursor / Claude Code / Codex** | По желанию | Локальный AI-агент, который читает SDD-спецификации |
| **Spec Kit (GitHub)** | Пока не подключать | Альтернатива с более развёрнутым процессом; не дублировать OpenSpec |
| **Kiro и системы вроде Jira/Notion** | Не нужны на первом этапе | Для этого репозитория сложнее, чем файлы + GitHub |

Опциональные инструменты не должны хранить ещё одну независимую копию плана: GitHub остаётся источником истины.

## Проверка качества до старта реализации

- [ ] У задачи есть ID из `PLAN.md` и понятная цель.
- [ ] Есть конкретные, недвусмысленные требования с `### Requirement:` и `#### Scenario:`.
- [ ] Для основного сценария и хотя бы одного отрицательного сценария ясно, как определить успех.
- [ ] Отмечены ограничения устройства, опасные воздействия, секреты и план восстановления.
- [ ] Каждое требование покрывается задачей/проверкой; ручные тесты отделены от автоматических.
- [ ] Не сказано, что прошивка поддерживает метод, без проверки на устройстве.
- [ ] Документы согласованы, не противоречат `AGENTS.md`; PR с изменениями привязан к change.
- [ ] **Не объединяем PR с потенциально опасной функциональностью, пока не оговорён способ отката.**

## Правила размерности

Один `change` = одна ограниченная, независимо проверяемая цель. Не описываем полностью весь унаследованный Free My TV заранее: сначала исследуем реальное поведение, затем формализуем только изменяемую часть. Для маленьких документационных исправлений достаточно PR и короткой проверки; для поведения на проекторе нужны полные требования и сценарии.
